# Reflection

In one test run, the harness received the request to find an apartment and passed it to the model adapter. The model selected the search tool and supplied the word “Apartment” as the query. The harness then called `execute_tool`, recorded the input and the returned envelope, and appended the event to `agent_runs.jsonl`. The response was successful, so the harness continued instead of treating the call as an error. In the offline test I used a MockModel that deliberately keeps returning a tool call. This made the step counter easy to check. After the configured maximum number of turns, the harness stopped with the `max_steps` reason. That limit is important because a model that keeps proposing actions should not be allowed to run forever. The safety test follows the same path, but the tool layer rejects a request that asks for private owner information. It returns `ok: false` and an error message rather than raising an exception. I kept the safety check inside `execute_tool` because that is the single entry point used by both the tests and the agent. This means the MCP wrappers and the agent receive the same protection. The retry benchmark is separate from the model loop: it tests whether temporary storage failures are retried within a bounded limit and records the latency and final outcome for every call.
